# The workout clock is synced history

A workout's duration is recorded in the same append-only history as its results, as `clock:<date>` events holding the seconds banked so far and the time the running stretch began (`{ elapsed, since }`), instead of in browser storage like the rest timer. Storing a start time rather than a ticking count keeps the clock right through reloads, a locked phone and a switch to another device, and a duration is something you compare across a program, as the program summary's average does. The app writes the stop itself: at the tick that completes the workout, when it is finished early, or at the last logged set once nothing has been logged for three hours, so a forgotten clock cannot record a day. Concurrent clock edits stay conflicts for review like any other, but the clock reads the newest version meanwhile, so a stop written by two devices never blanks it. The database's entity check had to admit `clock:`, so this needed a migration.
